# Журнал экспериментов

Все замеры — на библиотеке из 62 статей (33 англоязычные по speculative decoding, 29 русскоязычных по машинному обучению в медицине; 3844 фрагмента) и черновом золотом наборе `eval/retrieval_gold.jsonl` из 30 вопросов: 10 en→en, 10 ru→en (русский вопрос по английской статье), 10 ru→ru. Оборудование: RTX 3060 Laptop 6 ГБ, модели через LM Studio.

**Оговорка.** Вопросы набросаны по тексту фрагментов одним человеком и лексически близки к ответам — это завышает BM25. Набор ещё не проверен вторым человеком (статус `draft`).

## E1. Режимы поиска и модели эмбеддингов (6 октября 2026)

Команда: `uv run research-assistant eval-retrieval` с разными `EMBED_MODEL`. Recall@10 / MRR@10.

| Режим | Эмбеддинги | en→en | ru→en | ru→ru | Все |
|---|---|---|---|---|---|
| BM25 | — | 0.95 / 0.62 | 0.20 / 0.04 | 1.00 / 0.83 | 0.72 / 0.50 |
| Плотный | nomic-embed-text-v1.5 (англ., 137M) | 0.70 / 0.40 | 0.00 / 0.00 | 0.30 / 0.21 | 0.33 / 0.20 |
| Плотный | qwen3.5-0.8b (чат-модель, не эмбеддинговая) | 0.40 / 0.28 | 0.00 / 0.00 | 0.20 / 0.20 | 0.20 / 0.16 |
| Плотный | **bge-m3** (многоязычная, 567M) | 0.80 / 0.55 | **0.80 / 0.57** | 1.00 / 0.93 | 0.87 / 0.68 |
| Плотный | Qwen3-Embedding-0.6B (многоязычная, с инструкцией у запроса) | 0.50 / 0.29 | 0.60 / 0.16 | 0.90 / 0.65 | 0.67 / 0.37 |
| Гибрид RRF | Qwen3-Embedding-0.6B | 0.90 / 0.51 | 0.60 / 0.32 | 1.00 / 0.85 | 0.83 / 0.56 |
| Гибрид RRF | nomic-embed-text-v1.5 | 0.90 / 0.55 | 0.10 / 0.01 | 0.60 / 0.36 | 0.53 / 0.31 |
| Гибрид RRF | **bge-m3** | **1.00 / 0.68** | 0.80 / 0.49 | **1.00 / 0.90** | **0.93 / 0.69** |

Время запроса: BM25 — 1–4 мс, плотный и гибрид — около 30 мс (эмбеддинг запроса в LM Studio).

Выводы:

1. Англоязычная модель эмбеддингов не умеет межъязыковой поиск (ru→en = 0) и в гибриде тянет BM25 вниз: слабый плотный список «разбавляет» хороший.
2. Скрытые состояния чат-модели (qwen3.5-0.8b) — плохие эмбеддинги, хуже маленькой специализированной модели: её не обучали делать близкими векторы близких по смыслу текстов.
3. Многоязычная bge-m3 решает межъязыковой поиск (ru→en 0.00 → 0.80) и делает гибрид лучшим режимом (Recall@10 0.93). Принята по умолчанию. Qwen3-Embedding-0.6B (того же размера) на нашем наборе заметно слабее: 0.83 в гибриде, 0.60 на ru→en.
4. BM25 на русских статьях работает идеально благодаря стеммингу (Snowball), а на ru→en вытягивает только совпадающие термины (Saguaro, SpecVocab, GPT-2-L).
5. Слабое место гибрида — ru→en: когда списки не согласны, RRF чередует их, и BM25 подмешивает русские статьи с общими словами («модели»). MRR@10 гибрида на ru→en ниже, чем у чистого плотного поиска (0.49 против 0.57). Кандидаты на улучшение: взвешенный RRF, BM25 по переводу запроса (см. E3), реранкер.

## E3 (предварительно). Перевод запроса чат-моделью перед BM25 (6 октября 2026)

Скрипт: `uv run python eval/translate_queries.py qwen3.5-0.8b`. Русский вопрос переводится на английский, BM25 ищет по исходному запросу, по переводу или по обоим со слиянием RRF. Recall@10 / MRR@10.

| Запрос для BM25 | en→en | ru→en | ru→ru |
|---|---|---|---|
| Исходный | 0.95 / 0.62 | 0.20 / 0.04 | 1.00 / 0.83 |
| Перевод | 0.95 / 0.62 | 0.80 / 0.56 | 0.00 / 0.00 |
| Оба (RRF) | 0.95 / 0.62 | 0.70 / 0.35 | 0.90 / 0.63 |

20 переводов — 1598 токенов и 10 секунд. Модель на 0.8B переводит с ошибками («черновые модели» → «black hole models», выдуманные «15%»), но ключевые термины сохраняет, и этого хватает BM25.

Выводы:

1. Даже крошечная локальная модель как переводчик запросов даёт BM25 тот же Recall@10 на ru→en, что и многоязычные эмбеддинги.
2. Переводить нужно не всегда: по русским статьям перевод убивает поиск. Агенту нужно искать на языке документов или на обоих языках — это решение и проверим в E3 на этапе 5.
3. У Qwen3.5 в LM Studio нужно отключать «размышления» (`reasoning_effort: "none"`), иначе на коротких задачах весь лимит токенов уходит на рассуждение и ответ пустой.

Сравнение моделей-переводчиков (7 октября 2026), Recall@10 / MRR@10:

| Модель-переводчик | ru→en, перевод | ru→ru, оба запроса |
|---|---|---|
| qwen3.5-0.8b | 0.80 / 0.56 | 0.90 / 0.63 |
| qwen3.5-4b (Q4_K_M) | 0.90 / 0.63 | 0.90 / 0.57 |

Qwen3.5-4B переводит чище (без выдуманных чисел), и BM25 по её переводу находит на ru→en больше.

## Агент: первые прогоны и разбор ошибок (7 октября 2026)

Модель агента — Qwen3.5-4B Q4_K_M в LM Studio (контекст 16K, `reasoning_effort: none`), поиск — гибрид BM25 + bge-m3, лимит 12 шагов. Журналы прогонов — `runs/*.jsonl`.

### Ошибка 1. Зацикливание

Вопрос: «Почему спекулятивное декодирование хуже работает для малоресурсных языков и что можно сделать?» (`runs/ask-20261007-000137.jsonl`).

Агент сделал 4 поиска и 8 чтений фрагментов, исчерпал лимит в 12 шагов и не вызвал `final_answer`. На это ушло 81 тыс. токенов и 46 секунд. Нужные предложения были найдены уже на первом шаге. Совет в промпте («обычно хватает 1–3 поисков») маленькая модель без размышлений не выполняет: каждое новое наблюдение порождает ещё одно «уточнение».

Исправление в обвязке, а не в промпте: в конце каждого наблюдения агент видит остаток бюджета. После 6 поисков и чтений, а также на последнем шаге ему передаётся только инструмент `final_answer`. Повторный прогон: 7 шагов, 0 ошибок, 30 тыс. токенов, 27 секунд, 5 утверждений и 13 дословных цитат из двух нужных статей.

### Ошибка 2. Не те аргументы

(а) В том же первом прогоне агент передал в `read_passage` ID предложения (87383) вместо ID фрагмента: оба выглядели как голые числа. Исправление: у фрагментов префикс `p`, у предложений `s`; если в `read_passage` пришёл ID предложения, открывается фрагмент, где оно лежит.

(б) Вопрос «А какие ещё алгоритмы там сравнивали?» (`runs/chat-20261007-000435.jsonl`). Все поиски агент ограничил разделами `results` и `experiments`. У нужной статьи (CyberLeninka, без заголовков в тексте) весь текст лежит в разделе `body`, и фильтр его отсёк: агент ответил, что других алгоритмов в тексте нет. Исправление: текст без заголовков проходит любой фильтр по типу раздела. Повторный прогон: агент перечислил все сравниваемые методы (Naive Bayes, логистическая регрессия, линейный SVM, Random Forest, kNN) с цитатами.

### Ошибка 3. Утверждение не подтверждается цитатой

Там же, первый вопрос «Какой алгоритм лучше всего классифицировал мутации рака?». Агент написал «в литературе не указано, какой алгоритм лучший» и процитировал «Минимальное значение Logg-Loss получается при применении алгоритма kNN». Цитата дословная и действительно была в выдаче (механизм ID это гарантирует), но она опровергает утверждение, а не подтверждает его.

Механизм цитат по ID защищает от выдуманных и искажённых цитат, но не от неверных выводов из настоящих. Это измеряем отдельно: доля утверждений, которые подтверждаются своими цитатами (LLM-судья, откалиброванный на ручных метках), — этап оценки цитат.

## E6. Извлечение сущностей (7 октября 2026)

Задача: по тексту статьи найти методы, датасеты, метрики и задачи. Извлекает чат-модель со структурированным выводом (JSON-схема в LM Studio). Сущность остаётся, только если её название встречается в тексте — сравниваются основы слов подряд, поэтому русская «диагностика заболеваний» находится в «диагностике заболеваний», а выдуманная «chat reasoning» в «chat and math reasoning» — нет.

Золотой набор: `eval/entities_gold.jsonl`, 30 аннотаций (20 английских, 10 русских), 171 сущность; черновик, правила — в `docs/annotation_guidelines.md`. Команда: `uv run research-assistant eval-entities --model <модель>`. Строгое совпадение по основам слов, синонимы и сокращения засчитываются за одну сущность.

| Модель | Вариант | P | R | F1 | F1 en | F1 ru |
|---|---|---|---|---|---|---|
| qwen3.5-4b | без проверки по тексту | 0.60 | 0.76 | 0.67 | 0.74 | 0.51 |
| qwen3.5-4b | **с проверкой по тексту** | **0.64** | **0.76** | **0.70** | 0.76 | 0.54 |
| qwen3.5-0.8b | без проверки | 0.51 | 0.36 | 0.42 | 0.43 | 0.40 |
| qwen3.5-0.8b | с проверкой | 0.60 | 0.36 | 0.45 | 0.44 | 0.47 |

По типам у qwen3.5-4b с проверкой: датасеты P/R 1.00/1.00, методы 0.90/0.67, метрики 0.56/0.91, задачи 0.36/0.83.

Выводы:

1. Проверка по тексту — бесплатная точность: у 4B она убрала 13 ложных сущностей и не потеряла ни одной верной; у 0.8B — 18 ложных. Отброшенные — названия, которых в тексте нет («acceptance rate» в аннотациях, где он не упоминается), то есть знания модели «из памяти».
2. 0.8B для разметки непригодна: не находит ни одного датасета и почти ни одной метрики.
3. Основные ошибки 4B: метрики и задачи с размытыми границами («generation quality», «LLM inference», «autoregressive generation»). Это во многом вопрос правил разметки, а не модели: граница «задача / метод / область» — известная трудность разметки научных сущностей. Пропуски методов — в основном названия моделей (Qwen3-14B, LLaMA-2), которые модель не считает методами.
4. Формат «Approximate Speculative Decoding (ASD)» модель возвращает одной строкой; разбиение на полное имя и сокращение подняло F1 на 0.02.

Разметка библиотеки: 62 статьи, ~4 минуты на Qwen3.5-4B (вход — заголовок, аннотация, заключение и начало экспериментов, до 900 слов). Сущности привязываются ко всем фрагментам статьи, где встречаются, — фильтр поиска «фрагменты про MT-Bench» работает по всей статье при одном вызове модели на статью. После расширения входа экспериментами число найденных датасетов по теме выросло с 9 до 15+ (MT-Bench — 6 статей, Alpaca — 6, GSM8K — 5). Типичная ошибка типа на полной разметке: модели LLaMA и Vicuna записаны в датасеты.

## E1 (продолжение). Перевод запроса и реранкер в поиске (10 октября 2026)

Команда: `uv run research-assistant eval-retrieval --modes "hybrid,hybrid+translate,hybrid+rerank,hybrid+translate+rerank"`. Эмбеддинги bge-m3, чат-модель Qwen3.5-4B (LM Studio, GPU). Recall@10 / MRR@10, в последнем столбце — среднее время запроса.

| Режим | en→en | ru→en | ru→ru | Все | мс |
|---|---|---|---|---|---|
| Гибрид | 1.00 / 0.68 | 0.80 / 0.49 | 1.00 / 0.90 | 0.93 / 0.69 | 136 |
| Гибрид + перевод | 1.00 / 0.68 | **0.90 / 0.62** | 1.00 / 0.75 | **0.97** / 0.68 | 586 |
| Гибрид + реранкер | 0.90 / 0.49 | 0.80 / 0.68 | 0.90 / 0.72 | 0.87 / 0.63 | 5992 |
| Гибрид + перевод + реранкер | 0.90 / 0.49 | 0.90 / 0.64 | 0.90 / 0.81 | 0.90 / 0.65 | 6146 |

Выводы:

1. Перевод запроса — дешёвое и полезное дополнение для русских вопросов по английским статьям: ru→en Recall@10 0.80 → 0.90, MRR 0.49 → 0.62, около секунды на перевод. На ru→ru MRR немного падает (0.90 → 0.75): английский BM25-список добавляет шум, хотя в нём нет русских статей. Перевод стоит включать только для вопросов, ответ на которые ожидается в английских статьях.
2. Listwise-реранкер на Qwen3.5-4B (подход RankGPT) вредит: Recall@5 0.87 → 0.66, на en→en MRR 0.68 → 0.49, при этом 6 секунд на запрос. Маленькая модель плохо упорядочивает 20 кандидатов. Реранкер выключен по умолчанию; для проверки идеи нужен специализированный кросс-энкодер (bge-reranker-v2-m3), это ещё ~0,6 ГБ модели.

## E2. Цитаты по ID против цитат, которые пишет модель (10 октября 2026)

Команда: `uv run research-assistant eval-agent --variant quotes` (модель сама переписывает цитату в `final_answer`, ответ не проверяется) против `--variant agent` (цитаты по ID предложений). 30 золотых вопросов, Qwen3.5-4B, 1 прогон.

| Режим цитат | Дословных цитат | pass@1, по статье (95% ДИ) | pass@1, по фрагменту |
|---|---|---|---|
| По ID предложений | 1.00 (по построению) | **0.80** (0.63–0.90) | 0.30 |
| Текстом от модели | 0.96 | 0.63 (0.46–0.78) | 0.20 |

Выводы:

1. Если предложения в выдаче помечены ID, маленькая модель переписывает их почти дословно: 80 из 83 цитат (96%) найдены в библиотеке символ в символ. Три неточные: фраза обрезана многоточием, в русской цитате воспроизведён артефакт переноса из PDF («справ ляется»), одна английская цитата отличается от источника в середине. Перевода цитат на язык вопроса не было. Но и 4% — это ответы, где пользователь увидел бы «цитату», которой в статье нет.
2. Цитаты по ID дословны по построению, дешевле по выходным токенам и дают больше успешных ответов.

Оказалось, модель копирует предложение вместе с меткой из выдачи («[s84997] We introduce…»), и такая строка не находилась в тексте. После снятия меток — 96%. Вывод «модель искажает почти половину цитат» был бы ложным; метки снимаются в `evaluation/agent.py`.

## E3. Итеративный агент против однократного поиска (10 октября 2026)

Команды: `eval-agent --variant agent` (агент сам ищет, лимит 12 шагов) и `--variant single` (код делает один поиск по вопросу, k = 6, модель сразу отвечает). Успех — агент сдал ответ с цитатой: строго — из золотого фрагмента, мягко — из золотой статьи.

| Вариант | pass@1, по фрагменту | pass@1, по статье (95% ДИ) | Шагов | Токенов | Секунд |
|---|---|---|---|---|---|
| Итеративный агент | 0.30 | 0.80 (0.63–0.90) | 6.0 | 25 253 | 24.6 |
| Один поиск и ответ | 0.77 | 0.90 (0.74–0.97) | 1.0 | 2 489 | 8.3 |
| Поиск по вопросу заранее + агент (`prefetch`) | 0.70 | **0.97** (0.83–0.99) | 4.7 | 26 984 | 23.6 |

По группам (по статье): агент — en→en 0.90, ru→en 0.90, ru→ru 0.60; однократный — 1.00 / 0.90 / 0.80; prefetch — 0.90 / 1.00 / 1.00.

**Почему строгий критерий не годится для агента.** Разбор 21 «провала» итеративного агента показал, что в большинстве он ответил верно, процитировав другой фрагмент той же статьи: «up to 1.91× faster than SD» из раздела результатов вместо того же числа в заключении; английское тело русской статьи «The minimum value for log-loss is obtained…» вместо русской аннотации. Золотой набор отмечает один фрагмент, а ответ часто есть в аннотации, результатах и заключении сразу. Однократный поиск по самому вопросу находит именно золотой фрагмент, потому что вопросы написаны по его тексту. Поэтому основная метрика для агента — мягкая (цитата из золотой статьи), а строгая остаётся для оценки поиска. Настоящих ошибок у агента 6: цитаты из другой статьи (en07, xl01), соседние по теме, но не отвечающие на вопрос (en02, en04, ru03, ru08).

Выводы:

1. Чистый итеративный агент проигрывает однократному поиску (0.80 против 0.90) при в 10 раз большем числе токенов — пример тезиса «AI Agents That Matter» о том, что агента нужно сравнивать с дешёвой базовой линией. Причина видна в журналах: первый же запрос агент переформулирует и теряет формулировку вопроса, по которой находится лучший фрагмент.
2. Если отдать агенту поиск по самому вопросу в первом наблюдении и оставить ему инструменты (`prefetch`), получается лучшее из двух: 0.97 по статье и 0.70 по фрагменту — однократный поиск как сильная стартовая точка плюс возможность доискать. Цена — как у агента (~27 тыс. токенов, ~24 с). Этот режим включён по умолчанию в `ask` и `chat`. Разница с однократным поиском (0.97 против 0.90) в пределах интервалов на 30 вопросах — для уверенного вывода нужны повторы и больше вопросов (этап 9).
3. Набор вопросов благоприятен для однократного поиска: каждый вопрос написан по одному фрагменту и лексически близок к нему. Чтобы итеративность могла проявиться, нужны вопросы с ответом в нескольких статьях, перефразированные и сравнительные — их стоит добавить на этапе 9.

## E4. Локальная Qwen3.5-4B против облачной Mercury 3 (9 ноября 2026)

Команда: `eval-agent --variant prefetch` на тех же 30 золотых вопросах. Поиск в обоих прогонах гибридный (BM25 + bge-m3 в LM Studio); меняется только чат-модель агента. Qwen3.5-4B Q4_K_M — локально в LM Studio на RTX 3060 Laptop (6 ГБ), без размышлений. Mercury 3 — диффузионная LLM Inception Labs через OpenAI-совместимый API.

## E5. Диагностика Qwen3.5-4B и исправление промпта (9 ноября 2026)

Перед дообучением разобрали журналы всех прогонов Qwen3.5-4B: 60 прогонов оценки, режимы quotes/single, диалоги и журналы веб-интерфейса. Их сравнили с Mercury 3 на тех же 30 вопросах. Формат вызовов у Qwen безупречен: на 256 вызовов ноль ошибок инструментов, ноль путаницы p/s, ноль отклонённых `final_answer`. Ошибки — в решениях:

- **Не останавливается.** В `prefetch` золотой фрагмент был уже в стартовой выдаче в 27 из 30 вопросов, но в 16 из них модель продолжила искать. Сама она ни разу не ответила после собственного вызова: останавливали лимит или напоминание. На многошаговые прогоны ушло 95% токенов, а в 7 из них цитата ушла с уже найденного золотого фрагмента.
- **Фильтр разделов прячет ответ.** В `agent` модель ставит `section_kinds` в 96 из 106 поисков и ни разу не выбирает `abstract`, хотя золото — аннотация в 16 из 29 вопросов. Первый запрос отсёк тип золотого раздела в 20 из 30 вопросов. Так буквально применялся пример из промпта («results for numbers»).
- **`language=en` на русских темах.** 15 бесполезных поисков в 5 из 10 вопросов ru→ru.
- **Нет `not_found`.** Ни одного из 60. Когда ответа нет, модель уверенно отвечает по чужим статьям: 5 неверных выводов и 2 ответа «из памяти».
- **Повторы.** От 14% до 22% вызовов не дают новой информации, 9 точных повторов.

Исправления без обучения:
- новый промпт: «остановись, как только есть предложение с ответом», «не добавляй в запрос слов, которых нет в вопросе», «не ставь фильтры разделов и языка без просьбы», «нет ответа — `not_found`», «язык ответа — язык вопроса»;
- описания параметров инструментов;
- повтор вызова с теми же аргументами больше не выполняется: модель получает подсказку использовать уже найденное.

| | точно по фрагменту | по статье | шагов | токенов |
|---|---|---|---|---|
| Qwen, `agent`, старый промпт | 0.27 | 0.80 | 5.6 | 24 902 |
| Qwen, `agent`, новый промпт | **0.70** | **0.90** | **3.1** | **11 903** |
| Qwen, `prefetch`, старый промпт | 0.77 | 0.97 | 3.8 | 22 383 |
| Qwen, `prefetch`, новый промпт | 0.80 | 0.97 | **2.6** | **14 757** |
| Mercury 3, `prefetch`, новый промпт | 0.87 | 0.97 | 1.1 | 4 697 |

У Qwen с новым промптом формат вызовов по-прежнему безупречен: доля повторов 0–1%, язык ответа совпадает в 100% вопросов. Время на вопрос не сравниваем: GPU в это время делила другая сессия LM Studio.

Выводы:

1. Самая большая проблема чистого агента — фильтр разделов — снималась промптом, а не обучением. В варианте `agent` точность по фрагменту выросла в 2.6 раза при вдвое меньшем числе токенов. Дообучение нацелено на остаток: лишние шаги (2.6 против 1.1 у учителя), выбор предложения, которое буквально отвечает на вопрос, отказ `not_found`.
2. **Учитель нарушает правило языка.** Mercury 3 отвечал по-русски на 6 из 10 английских вопросов даже с явным правилом в промпте. С подсказкой, которую видит только учитель («вопрос на английском, отвечай по-английски, без разметки»), — 10 из 10. При сборе траекторий подсказка добавляется к системному промпту, при экспорте промпт заменяется штатным. Ученик учится ровно на входе деплоя.
3. **Ошибка измерения.** Прогоны Mercury и Qwen, запущенные в одну секунду, писали в один журнал `eval-agent-<вариант>-<секунда>.jsonl`. Отчёты при этом верны: метрики считаются по событиям внутри процесса. Но журнал этих двух прогонов перемешан и для `--rescore` не годится. Теперь в имени журнала есть модель и PID.

## Разбор живых прогонов и доработки без изменения промпта (14 ноября 2026)

Поводы: три прогона `ask` на теме `resto-gen` (Mercury 3, `runs/ask-20261114-005*.jsonl`) и замечание пользователя: поиск по фрагментам отвечает на «что сделано в статье» и плохо — на «чего в ней нет»; ход рассуждения теряется; числа из таблиц склеены.

Что видно в журналах:

- **Плотного поиска не было.** На этой машине в LM Studio нет bge-m3, все три прогона шли на BM25 с пометкой «Semantic search is unavailable». Инструмент `find_papers` при этом падал с `BadRequestError: 400`, а не откатывался.
- **Выдача обрезалась.** Стартовая выдача (6 фрагментов) не помещалась в 6000 символов и резалась посреди предложения.
- **Язык.** На два английских вопроса из трёх Mercury 3 ответил по-русски (то же, что в E5).
- **Отрицательный вывод без оговорок.** «Ни одна статья в библиотеке не измеряет…» — по шести фрагментам на один запрос.
- **Таблицы.** `Density 0.60 0.79 0.73 Entropy 0.65 …` одним абзацем; таблица из одних чисел отброшена как формула.

Что сделано (`SYSTEM_PROMPT` и `SCHEMAS` не менялись, `prompt_hash` прежний):

| Проблема | Решение |
|---|---|
| Нет эмбеддингов или индекс неполный | BM25 по переводу запроса в обе стороны, включается сам; `find_papers` не падает |
| Обрезка выдачи, мало шагов на вопрос из нескольких частей | у облачной модели 12 поисков и 14000 символов; обрезка по границе строки |
| Язык и полнота ответа | подсказки `agent/prompts.answer_hints` для облачной модели |
| «Чего нет» | `coverage`: вердикт по каждой статье темы с переформулировками аспекта и границами проверки |
| Ход рассуждения, расхождения | `read`: вся статья по порядку, отчёт с «чего нет» и расхождениями |
| Таблицы | парсер v2: строки таблицы по геометрии, строка = цитируемое предложение |

Проверка на живой модели (по одному прогону, не оценка):

- Тот же английский вопрос про Gogolev–Ozhegov: ответ по-английски, 3 шага, 0 ошибок инструментов, 16.8 тыс. токенов.
- `read 136` (PolyLayout, 226 предложений, одно окно, 11.6 тыс. токенов, 5 с): находки с цитатами, три пункта «чего нет» по заданным аспектам и расхождение 2.74 в тексте против 2.73 в таблице 4 с пояснением авторов.
- `coverage "расстановка мебели в помещении непрямоугольной формы" --topic resto-gen --limit 25` (26 вызовов, 42.6 тыс. токенов, 27 с): «рассматривают» — PolyLayout и ATISS (эксперимент с нестандартными планами), «частично» — LayoutGPT (только прямоугольные), LayoutVLM. Вывод «в литературе этого нет», сделанный до чтения PolyLayout, такая проверка не пропускает.
- Таблицы: в 72 PDF темы `resto-gen` найдено 387 таблиц, 3171 строка; заметно уменьшился обычный текст только у одной статьи (таблицы ушли в отдельные фрагменты).

Ограничения. Золотой набор не перепрогонялся: ему нужен bge-m3, а PDF его статей на этой машине нет. `coverage` судит по лучшим фрагментам статьи, а не по полному тексту, и только по библиотеке. Таблицы без чисел и формулы разбираются по-прежнему как текст; в формулах остаётся мусор LaTeX из PDF.
